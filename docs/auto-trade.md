## Functional requirements and qualification

An eligible user can connect an authorized provider, select a real approved model and markets, configure stake and risk, schedule or start a session, monitor and stop it, and inspect verifiable history. Store versioned configuration, owner, provider, model/version, ordered market rules, stake method, initial stake, filters, schedule, limits and explicit consent. Expose only implemented, approved, non-demo models with supported markets, parameter schema, publication and freshness semantics, historical sample, period and caveats. No live model currently qualifies. A confidence/risk filter is offered only where the model defines it; missing required data fails closed. Neither historical performance nor confidence guarantees results.

Canonical markets are over 1.5, under 3.5, over 2.5, under 2.5, GG and NG. Each enabled market needs real prediction and settlement support and a versioned, verified mapping from canonical fixture, market, line and outcome to the authorized provider's identifiers. Offer priority, confidence and odds bounds. Never send display labels as provider identifiers. Default to one selection per provider account and fixture across configurations; correlated or multiple selections require explicit policy and aggregate exposure limits.

Qualify deterministically and record rejection reasons: active consent and entitlement; valid session and schedule; approved model and immutable prediction published before kickoff; matching fixture and open market; prediction and quote freshness and kickoff buffer; required confidence/risk filters; allowed actual odds; verified connection and available balance; deduplication and central risk. Provider-specific freshness, buffer and balance TTL require approval. Unknown, stale, suspended or missing data rejects the order. Recheck time-sensitive conditions immediately before submission.

### Optional loss observation gate (proposed)

The user may enable a virtual-loss condition: at least `L` losses among the most recent `N` eligible, settled predictions, with `1 <= L <= N <= 100`. These are observed prediction outcomes, including predictions not bet on; they are not financial losses or actual bets. The preview saves this configuration only in the current tab; it performs no observation and does not activate trading. The gate is an entry filter, not a guarantee, predictive signal or replacement for risk limits. Count losses within the window, not necessarily consecutive losses. The upper bound is a proposed validation limit for review.

Proposed scope is the session's immutable platform, league, market and model/version. A prediction counts once only if genuinely published before kickoff and its authoritative outcome is known. Order by event kickoff then stable prediction ID, not settlement delivery order. Require a complete N-result window from verified data; missing, disputed or stale results block the gate. Voids, cancelled fixtures and unsettled predictions do not count. Do not use synthetic or outcome-selected fixtures for live decisions. Do not backfill using forecasts generated after the event. For simultaneous events, only consume results as confirmed and pause on unresolved ordering if necessary. Duplicates are ignored; corrections trigger a rebuild of the affected window and pause until consistent.

At session start, `observing_initial` blocks bets until a complete N-result window contains at least L losses; then move to `eligible`. After a placed bet is authoritatively settled as a loss, atomically enter `observing_after_loss` and immediately block new submissions. Rebuild the rolling window from eligible outcomes available at or after that loss; when it contains at least L losses, move to `awaiting_observed_win`. A later, distinct observed win moves the gate back to `eligible`; it does not itself place a bet. If a later placed bet loses, repeat the cycle. A win used to resume must occur after the loss condition was first met, and may be unbet. Unknown or void order outcomes do not count as placed-bet losses. All normal eligibility, entitlement, account, session and risk checks still run before every submission. This is an explicit interpretation of the requested behavior; product should confirm whether the threshold counts non-consecutive losses and whether the placed losing bet is included in the post-loss window before backend implementation.

To prevent multiple bets escaping a loss-triggered pause before settlement, enable this mode only with a maximum of one unsettled or unknown order per session, and enforce that reservation under the account/session lock. A dispatch already in flight cannot be recalled. Manual pause, stop, session end, disconnection, risk or entitlement failure overrides the observation gate; observations never automatically resume a manually paused or risk-stopped session. New session starts a fresh initial evaluation; no automatic carryover. Persist policy snapshot, gate state/version, threshold event, observation cursor, event IDs and audit reasons. Apply ordered outcomes and gate transitions idempotently in the same transaction as reservation/session checks; rebuild after restart from durable verified inputs, fail closed on gaps or corrections. A product decision is needed on cross-session history and how to handle late/out-of-order results in the live provider contract.

Backend acceptance tests must cover disabled gate, incomplete window, exactly L losses, fewer than L, non-consecutive losses, eligible transition, losing placed bet, waiting for a later observed win, repeated cycles, duplicate/out-of-order/corrected outcomes, voids, conflicting manual/risk stops, concurrent workers, unknown orders, restart and lack of real prediction data. Verify no submission can bypass the gate and no observation is shown as an actual wager.

## Stake and risk rules

Use integer minor units, decimal strings in JSON, and exact fixed-point odds at provider precision. Check currency, increment, minimum, maximum and overflow; never use floating-point money. Strategies return proposed stakes and explanations only; all proposals pass the same risk manager. Fixed stake uses the configured initial amount. Percentage stake is `floor(verified_available_balance * basis_points / 10000)` rounded down to the provider increment. Every configuration still defines a positive initial amount; its role in percentage mode requires approval. Never silently increase a stake to satisfy a provider minimum.

* **Flat:** initial amount, or an independently approved percentage basis, without loss progression.
* **Martingale:** after each confirmed qualifying loss, `initial * multiplier^step`, rounded down to the increment. Win resets; void/refund does not advance. Enforce approved max steps, individual stake, cumulative recovery exposure and available balance. Exceeding a limit pauses progression and the session; do not silently cap and imply recovery. Partial settlement requires an approved provider-specific rule.
* **Recovery:** track sequence realized net including verified fees; `outstanding = max(0, -sequence_net)`. With approved extra target `E` and decimal odds `o > 1`, propose `ceil((outstanding + E) / (o - 1))` to the provider increment using exact arithmetic. A win reduces outstanding by actual net profit, a loss increases it, and a refund contributes zero. Reset once outstanding and the approved extra target are satisfied, or on explicit termination. Track attempt count and cumulative exposure; terminate on limits, session end, emergency stop or unreliable results. Permit one unsettled order per recovery sequence. Corrections quarantine progression until reconciled. Example: outstanding 1,000 minor, extra 100, odds 2.00, increment 100 yields 1,100 minor before risk checks. No progression guarantees recovery or profitability.

Realized net is the sum of authoritative settled net amounts, fees and corrections. Unsettled exposure is the worst-case stake loss on reserved, submitted, accepted and unknown orders; it is not profit. Reserve exposure before submission and retain unknown-order reservations until authoritative resolution. Session profit target uses realized net; stop-loss triggers when realized net is at or below the negative limit. Already submitted or in-flight orders can settle later, so these limits cannot guarantee the final loss. A conservative additional gate checks `realized loss + outstanding worst-case + proposed stake <= session loss budget`, plus daily and account limits, without double counting settled reservations. Define daily boundary and treatment of gains through approved policy.

Require approved maximum stake, session and daily exposure/loss, consecutive losses, bets per session, progression, minimum verified balance, unsettled count, correlated exposure and emergency stop. Percentage limits use a fixed verified session-bankroll snapshot, not wallet credit. Check at start, reservation, final dispatch, settlement/correction and connection/entitlement change. Account-level locking serializes competing configurations. A stop blocks new dispatches, terminates progression, records reason and notifies; outstanding orders continue reconciliation and can change final P&L without restarting the session.

## Sessions and scheduling

Recommend half-open local slots Night [00:00,06:00), Morning [06:00,12:00), Afternoon [12:00,18:00), Evening [18:00,24:00). Product must confirm the change from the originally requested overlapping 16:00 evening start. Store IANA zone and UTC instants; snapshot zone, local date, resolved UTC boundaries and policy version. A zone change affects future sessions only. Proposed DST policy shifts nonexistent boundaries to the first valid instant, chooses the earlier instant for ambiguous starts and later for ends, and rejects resulting overlap or excess duration; this needs approval. A unique `(configuration, schedule version, local date, slot)` prevents duplicate occurrences. Initially allow one active session per configuration and one per provider account, enforced transactionally. Due jobs use leases and UTC, recheck entitlement and state, skip starts beyond an approved grace window and never backfill bets.

| From | To | Initiator and condition |
| --- | --- | --- |
| draft | scheduled | Owner saves a valid schedule; no submission authority yet. |
| draft/scheduled | starting | Owner or scheduler claims an eligible occurrence and checks prerequisites. |
| starting | active / failed | Session service validates all gates or records failure. |
| active | paused | Owner or safety service closes new-dispatch gate; reconciliation continues. |
| paused | active | Owner resumes after all checks, within the original boundary; risk stops do not auto-resume. |
| starting/active/paused | stopping | Owner, boundary, entitlement, emergency or risk service immediately closes gate. |
| stopping | stopped / completed / stopped_profit / stopped_loss / stopped_risk / failed | Service records reason. Completed means the scheduling window ended, not that all bets settled. |
| scheduled | stopped | Owner cancels occurrence. |

Transitions use versioned compare-and-swap under lock. Terminal sessions never reactivate; late settlements update projections without changing termination reason. Pausing does not extend the session. A stop cannot recall a request already in flight; track and reconcile it. Restart scans expired leases, reservations, unknown orders and due sessions; never automatically replay an unknown submission.

## Architecture and provider feasibility

Proposed modular PHP services behind thin authenticated controllers and injected repositories: configuration/consent; sessions/scheduler; prediction qualification and market mapping; independent stake strategies; central account risk/reservation; platform connection/capability registry; execution/reconciliation; settlement/analytics; notifications/audit. Existing repository and clock contracts inform boundaries but do not provide production guarantees. Initially use one modular deployment, MySQL transactions and durable workers/outbox; introduce distributed infrastructure only when justified. An open browser is not required.

Flow: published prediction → eligibility → current quote/balance → pure stake proposal → locked risk check and durable intent/reservation → dispatch gate recheck → authorized provider order → acknowledgment/unknown → provider query or verified webhook → settlement → risk/progression and analytics → outbox notification. An adapter advertises supported authentication, balance, fixtures, markets, quotes, submission, idempotency, lookup, history, settlement, revocation, limits and webhook verification, with provenance, version and expiry. Unsupported operations return explicit unavailable. Live execution requires a reliable method to resolve uncertain outcomes.

SportyBet's [Nigeria terms](https://www.sportybet.com/ng/help?nav=terms-and-conditions&subNav=anti-money-laundering) restrict interference including robots and security bypass. This does not establish an authorized integration or prove no private partnership API exists. Obtain written permission and a scoped contract. BetPawa and BetKing automation permission and capabilities are unverified. Record owner, agreement, jurisdiction, allowed methods, source, date and expiry for every enabled capability. No scraping, private endpoint, CAPTCHA circumvention or impersonation substitutes for permission.

Execution states are `reserved → dispatching → accepted | rejected | unknown`; accepted progresses to settled or provider-confirmed void. Unknown resolves through authoritative provider lookup/history or documented investigation. Persist intent, client order key, quote/version, stake, risk snapshot and attempt before network I/O. A business deduplication key covers owner/provider account/fixture/market/selection and approved policy scope; also use a provider client key when supported. Lock the account guard and commit risk checks and reservation before calling the provider. A fenced worker rechecks stop epoch, entitlement and quote before a single submission. A stop can race a request already sent; reconcile that request. On timeout or crash after dispatch, mark unknown; never blindly retry. Retry only when the provider proves absence and its contract supports safe lookup/idempotency, and fresh risk and quote checks pass. Otherwise quarantine and escalate. Accepted requires a provider reference; rejected releases reservation only on authoritative evidence. Verify webhook signatures, deduplicate provider event/version, reconcile against provider queries and append settlement corrections. Mismatches pause affected accounts and alert operations.

Proposed InnoDB tables use opaque IDs, UTC `DATETIME(6)`, foreign keys, ownership checks, bounded integer minor amounts and versioned policy snapshots. JSON documents require validated schemas and indexed scalar query fields. No migration framework is implemented yet.

| `trade_market_rules` | Version, canonical market, priority, odds/confidence bounds; unique version/market and version/priority. |
| `trade_schedules` | Version, IANA zone, slot, enabled; unique version/slot; indexed resolved due occurrences. |

| `trade_account_guards` | One lockable row per provider account, stop epoch, active claim, reserved exposure and version. Enforce conditional concurrency through this row rather than assuming MySQL partial indexes. |
| `trade_orders`, `trade_order_attempts` | Session/connection/prediction, canonical/provider identifiers, quote, stake, state, client key, provider reference, risk snapshot; unique business key and provider/client key; provider-scoped reference uniqueness and state/lease indexes. |

Provider mappings and prediction provenance belong to their owning catalog/ingestion modules. Update order, reservation, progression and session counters atomically under consistent account guard → session → order lock order; retry deadlocks before any provider call. Publish via transactional outbox and deduplicate consumers. Rebuild and compare projections to immutable records; quarantine mismatches. Use versioned additive migrations after shared identity/catalog foundations, test fresh install, upgrade, backup and restore; after real writes use forward corrections. Legal must approve retention/deletion. Do not backfill demo records.

## REST API

Proposed `/api/auto-trade` routes use HTTPS, authenticated same-origin session, CSRF on mutations, owner inferred from session, object-level checks, no-store responses and shared per-user/IP rate limits. Administrative routes require separate RBAC. Preserve `{data,error,meta}` without changing the existing prediction API's string errors. New errors are `{code,message,details}`; meta contains request ID and cursor. Amounts are decimal strings in minor units, odds fixed-point strings, timestamps ISO UTC. Lists use opaque stable `(created_at,id)` cursors, default 25/max 100, bounded allowlisted filters. Never trust client balance, account ownership, settlement or odds.

Mutations require a bounded `Idempotency-Key` unique per owner/operation: same key and canonical payload returns the prior result, changed payload or in-progress returns 409. Updates and transitions require `If-Match` version. Audit successful and rejected privileged mutations without secrets. Responses: 400 malformed, 401 authentication, 403 authorization/CSRF, 404 inaccessible or missing, 409 state/version/idempotency conflict, 422 invalid/ineligible, 429 with `Retry-After`, 503 dependency unavailable. Stable codes include `PROVIDER_UNAVAILABLE`, `ENTITLEMENT_REQUIRED`, `RISK_LIMIT`, `STALE_QUOTE`, `ORDER_UNKNOWN` and `SESSION_CONFLICT`. Apply stricter configurable limits to connect/start operations; operational values need approval.

| Method and route | Request, response and special rules; mutations emit corresponding audit events |
| --- | --- |
| GET `/capabilities` | Optional provider; returns available model/market/provider capability catalog and unavailability reasons. |
| POST `/configurations` | Config object; 201 `{id,version,status}` after model, ownership, market and limit validation; `config.created`. |
| GET `/configurations`, GET `/configurations/{id}` | Owner-scoped list with cursor or `{id,version,config,status}`. |
| PUT `/configurations/{id}` | Full config and If-Match; new immutable version; existing session keeps its snapshot; `config.updated`. |
| DELETE `/configurations/{id}` | If-Match; 204 for inactive configuration without pending work; logical delete, `config.deleted`. |
| POST `/configurations/validate` | Config; `{valid,errors,warnings}` without reservation or execution. |
| POST `/connections` | `{provider,return_uri_id}`; approved delegated flow returns `{id,authorization_url,state_expires_at}`; `connection.initiated`. |
| GET `/connections`, GET `/connections/{id}` | Owner-scoped status, capabilities and expiry; never tokens. |
| POST `/connections/{id}/reconnect` | `{return_uri_id}` and delegated authorization details; audit reconnect. |
| DELETE `/connections/{id}` | 202 status; close dispatch gate immediately, revoke if supported and reconcile outstanding orders; audit disconnect. |
| POST `/sessions` | `{configuration_id,mode,occurrence_id?}`; 201 session; validate ownership and schedule; audit creation. |
| POST `/sessions/{id}/start`, `/pause`, `/resume`, `/stop` | `{reason?}`, version and idempotency; 202 `{id,status,version}`; validate transition and start/resume gates; audit transition. |
| POST `/emergency-stop` | `{connection_id?,reason}`; 202 `{stop_epoch,affected_count}`; close owner-scoped gates before asynchronous work; audit. |
| GET `/sessions`, GET `/sessions/{id}` | Cursor/status filters; owner-scoped state, snapshot, timing, reason, limits, realized net and exposure. |
| GET `/orders`, GET `/orders/{id}` | Bounded session/status/date filters and cursor; intent, provider reference, odds, stake, state, settlement and progression; no secrets. |
| GET `/sessions/{id}/performance`, `/risk-events`, `/activity` | Bounded filters/cursor; owner-only, realized and outstanding separate. |
| GET `/strategies/performance` | Model/strategy/date filters; verified live results separated from simulation, sample and as-of. |

Illustrative request: `{"connection_id":"conn_1","model_id":"approved_model","model_version":"1","markets":[{"market_id":"over_15","priority":1,"min_odds":"1.50","max_odds":"2.00","min_confidence":null}],"staking":{"method":"flat","initial_minor":"10000","currency":"NGN"},"risk":{"max_stake_minor":"10000","session_loss_minor":"50000","session_profit_minor":"30000","max_unsettled":1},"schedule":{"timezone":"Africa/Lagos","slots":["morning"]},"consent_version":"v1"}`. Values illustrate shape, not defaults; production validation requires the complete approved risk policy. Response: `{"data":{"id":"cfg_1","version":1,"status":"draft"},"error":null,"meta":{"request_id":"req_1"}}`. Delegated callbacks validate state/PKCE, issuer, expiry, allowlisted redirect and replay, then bind to the initiating user. Webhooks use provider signatures, replay windows and inbox deduplication rather than user session authentication.

## User experience and alerts

Reuse the shared shell, breadcrumb, dark/green visual language, compact cards, dialogs and responsive table/card patterns. Begin with availability, connection status and explicit unavailable reasons; show configuration selector, session state, model/markets, strategy and controls, realized P&L versus unsettled exposure, limits and recent activity. Progressive setup: connection → model/markets → stake → schedule → risk → review/consent. Expand advanced recovery and market options on demand. Show verified source, as-of time, odds, currency, caps and uncertainty; label simulations separately from verified provider records. Disabled prerequisites must not resemble an active account. Accessible confirmations explain start/resume, risk-increasing changes, disconnect and emergency stop, including in-flight orders. Keep emergency stop reachable without the wizard.

Monitoring shows start/end in user zone, state/reason, connection health, risk limits, progression, unknown orders, outstanding exposure and last update. Searchable/paginated history shows fixture, league, model, market, provider odds, stake, status, settlement, net, progression and provider reference. Desktop semantic tables become labeled mobile cards. Provide keyboard/focus management, labels, error summaries, screen-reader status, contrast, reduced motion and loading, empty, stale, reconnect and failure states. Use bounded polling initially, stop when hidden, and indicate staleness; the browser does not operate workers.

Critical alerts: stop-loss, risk/emergency stops, unknown order, disconnection, insufficient balance, entitlement loss and execution failure. Informational alerts: link, session start/pause/stop, submission/rejection/settlement, profit target and progression termination. Use durable in-app and approved channels, deduplicate by event ID, honor approved preferences without suppressing required safety notices. Delivery failure never changes financial state. The notification service is a dependency, not implemented.

## Security, entitlement and operations

Approved identity/compliance services must supply strong authentication, age/jurisdiction and self-exclusion checks; fail closed when unavailable. Versioned consent covers provider, limits, actions and revocation; renewed consent is required for material changes where applicable. Store tokens only server-side using envelope encryption with KMS-managed rotating keys, restricted service identities, TLS, redacted logs and audited access. Never store plaintext passwords or send provider credentials to clients. Prefer approved delegated access. Apply least-privilege RBAC, rate limits, tamper-evident audit, anti-replay and incident revocation. Simora does not hold or transfer provider funds. The [Nigeria Data Protection Act](https://www.ndpc.gov.ng/ndp-act-2023/) and [FCT betting permit guidance](https://lro.abj.gov.ng/sports-betting-permit/) are starting points, not licensing conclusions; counsel must determine applicable federal/state rules, obligations and current regulator guidance. Approve retention, breach response and deletion while preserving legally required records.

Billing owns authoritative entitlement. Auto Trade reads a versioned decision for access, models, configurations, sessions, connections and history; plan mappings and values remain unresolved. Recheck at activation, reservation and dispatch. Expiration, suspension or unverified entitlement closes the gate, while reconciliation and authorized history continue. Cancellation effective at period end follows the authoritative effective time. A transient outage fails closed for new orders; do not infer grace from a billing preview. Subscription wallet credit is never bookmaker bankroll.

Durable jobs claim sessions, evaluate predictions, refresh quotes/balances, submit, reconcile unknown/accepted orders, apply settlements, stop sessions and dispatch notifications. Safe reads use bounded retries with jitter, leases and dead-letter alerts; provider writes obey the stricter unknown-order rule. Fencing and persisted state prevent replay after lease expiry. Authorized admins can view aggregate health, queue age, provider outages, risk events, unresolved orders and audit; suspend a user/provider or activate global stop with reason and audit. They cannot view credentials or bet for users. Two-person approval for global re-enable is recommended pending policy. Stop gates stay closed on restart.

Measure queue lag, failures, stale data, provider latency, unknown-order age, mismatches, duplicate attempts, risk stops, entitlement failures and worker heartbeat; approve alert thresholds, owners and SLAs. Incident response closes gates, preserves in-flight references, reconciles with providers, notifies affected users, records investigation and requires reviewed reopening. Test encrypted backups and restore, approve RPO/RTO, and never blindly replay restored order queues.

## Simulation and verification

Use isolated storage and simulated provider with clear UI/API provenance. Current outcome-selected fixtures exercise mechanics only; they cannot measure strategy performance. Valid backtests require immutable predictions actually available before kickoff, timestamped executable historical odds, settlements, fees, increments, suspensions, delays and a declared fill model. Use chronological evaluation and as-of joins; report missing data, selection bias, sample, drawdown, losses, exposure and uncertainty. Simulations never submit live orders or update live P&L.

Deterministic unit tests cover eligibility, mapping, rounding, caps, progression/reset/void/correction, stop thresholds and lifecycle. Integration tests use mock providers and a real transactional database to race workers, duplicate events, scheduler/DST boundaries, stop versus dispatch, entitlement changes, account limits, restarts at each commit/network boundary and out-of-order settlements. Contract tests cover API ownership/CSRF, idempotency, validation and rate limiting; provider tests require an authorized sandbox. UI tests cover keyboard, mobile, loading, stale, unknown and confirmation states. Load tests honor agreed provider limits and avoid real bets. Run existing PHP/JS regression suites.

Acceptance: no duplicate submissions in injected race/retry scenarios; every order has a prior committed risk decision and reservation; unknown submissions remain reserved and are never retried without authoritative proof of absence; cross-owner access is denied; stop blocks new dispatch claims while in-flight orders remain tracked; duplicate or corrected settlement produces exactly one effective net change; schedule occurrences remain unique across DST/restarts; demo data cannot enter live execution; secrets never appear in API/logs. Already in-flight or unsettled bets can still produce losses after a stop.

Definition of Done for each capability: approved rules/contracts, automated tests and ownership, security review, observable failure paths, migration/restore rehearsal, accessibility where applicable, documentation and default-off feature flag. Live execution additionally requires provider/legal sign-off and a controlled release decision.
